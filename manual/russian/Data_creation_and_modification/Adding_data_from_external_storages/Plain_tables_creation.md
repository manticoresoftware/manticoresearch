# Создание обычных таблиц

Обычные таблицы создаются один раз путем загрузки данных при создании из одного или нескольких источников. Обычная таблица неизменяема, поскольку в течение ее срока жизни в нее нельзя добавлять или удалять документы. Можно только обновлять значения числовых атрибутов (включая MVA). Обновить данные можно только пересозданием всей таблицы.

Обычные таблицы доступны только в [обычном режиме](../../Creating_a_table/Local_tables.md#Defining-table-schema-in-config-%28Plain mode%29), и их описание состоит из объявления таблицы и одного или нескольких объявлений источников. Сбор данных и создание таблицы выполняются не сервером `searchd`, а вспомогательной утилитой `indexer`.

**Indexer** — это инструмент командной строки, который можно запускать напрямую из командной строки или из shell-скриптов.

При запуске он может принимать ряд аргументов, а также имеет несколько собственных настроек в конфигурационном файле Manticore.

В типичном сценарии `indexer` делает следующее:
* Получает данные из источника
* Строит обычную таблицу
* Записывает файлы таблицы
* (Необязательно) Сообщает поисковому серверу о новой таблице, что запускает ротацию таблицы

## Инструмент Indexer
Инструмент `indexer` используется для создания обычных таблиц в Manticore Search. Общий синтаксис такой:

```shell
indexer [OPTIONS] [table_name1 [table_name2 [...]]]
```

При создании таблиц с помощью `indexer` файлы сгенерированных таблиц должны иметь права, позволяющие `searchd` читать, записывать и удалять их. В официальных пакетах Linux `searchd` запускается от пользователя `manticore`. Поэтому `indexer` тоже должен запускаться от пользователя `manticore`:

```shell
sudo -u manticore indexer ...
```

Если вы запускаете `searchd` иначе, возможно, вам нужно опустить `sudo -u manticore`. Просто убедитесь, что у пользователя, от имени которого работает экземпляр `searchd`, есть права на чтение и запись для таблиц, сгенерированных с помощью `indexer`.

Чтобы создать обычную таблицу, нужно перечислить таблицы, которые вы хотите обработать. Например, если ваш файл `manticore.conf` содержит сведения о двух таблицах, `mybigindex` и `mysmallindex`, можно выполнить:

```shell
sudo -u manticore indexer mysmallindex mybigindex
```

Можно также использовать шаблоны с подстановочными знаками, чтобы сопоставлять имена таблиц:

* `?` соответствует любому одному символу
* `*` соответствует любому количеству любых символов
* `%` соответствует нулю или одному любому символу

```shell
sudo -u manticore indexer indexpart*main --rotate
```

Коды выхода `indexer` такие:

* 0: все прошло успешно
* 1: во время индексирования возникла проблема (и если был указан `--rotate`, он был пропущен) либо операция выдала предупреждение
* 2: индексирование прошло успешно, но попытка `--rotate` завершилась неудачей

### Служба Indexer systemd

Запустить `indexer` можно и с помощью следующего unit-файла `systemctl`:

```shell
systemctl start --no-block manticore-indexer
```

Или, если нужно построить конкретную таблицу:

```shell
systemctl start --no-block manticore-indexer@specific-table-name
```

Используйте команду `systemctl set-environment INDEXER_CONFIG`, чтобы запускать Indexer с пользовательской конфигурацией, которая заменяет настройки по умолчанию.

Команда `systemctl set-environment INDEXER_ARGS` позволяет добавить пользовательские параметры запуска для Indexer. Полный список параметров командной строки см. [здесь](../../Data_creation_and_modification/Adding_data_from_external_storages/Plain_tables_creation.md#Indexer-command-line-arguments).

Например, чтобы запустить Indexer в тихом режиме, выполните:
```bash
systemctl set-environment INDEXER_ARGS='--quiet'
systemctl restart manticore-indexer
```

Чтобы отменить изменения, выполните:
```bash
systemctl set-environment INDEXER_ARGS=''
systemctl restart manticore-indexer
```

### Параметры командной строки Indexer
* `--config <file>` (`-c <file>` кратко) указывает `indexer` использовать заданный файл как конфигурацию. Обычно он ищет `manticore.conf` в каталоге установки (например, `/etc/manticoresearch/manticore.conf`), а затем в текущем каталоге, из которого вы вызываете `indexer` из shell. Это особенно полезно в общих средах, где бинарные файлы установлены в глобальный каталог, например `/usr/bin/`, но вы хотите дать пользователям возможность создавать собственные пользовательские конфигурации Manticore, либо если вы хотите запускать несколько экземпляров на одном сервере. В таких случаях можно разрешить им создавать собственные файлы `manticore.conf` и передавать их в `indexer` с помощью этого параметра. Например:

  ```shell
  sudo -u manticore indexer --config /home/myuser/manticore.conf mytable
  ```

* `--all` указывает `indexer` обновить все таблицы, перечисленные в `manticore.conf`, вместо указания отдельных таблиц. Это полезно в небольших конфигурациях или в cron-подобных задачах обслуживания, где весь набор таблиц перестраивается каждый день, каждую неделю или с любым другим подходящим периодом. Обратите внимание: поскольку `--all` пытается обновить все найденные в конфигурации таблицы, он выдаст предупреждение, если встретит таблицы RealTime, и код выхода команды будет `1`, а не `0`, даже если обычные таблицы завершились без ошибок. Пример использования:

  ```shell
  sudo -u manticore indexer --config /home/myuser/manticore.conf --all
  ```

* `--rotate` используется для ротации таблиц. Если только вы не можете отключить функцию поиска, не мешая пользователям, вам почти наверняка нужно оставить поиск доступным во время индексирования новых документов. `--rotate` создает вторую таблицу параллельно первой (в том же месте, просто с добавлением `.new` в имена файлов). После завершения `indexer` уведомляет `searchd`, отправляя сигнал `SIGHUP`, и `searchd` пытается переименовать таблицы (переименовывая существующие с добавлением `.old` и переименовывая `.new`, чтобы заменить их), а затем начинает обслуживать более новые файлы. В зависимости от настройки [seamless_rotate](../../Server_settings/Searchd.md#seamless_rotate) может быть небольшая задержка перед тем, как станут доступны для поиска новые таблицы. Если одновременно ротируется несколько таблиц, связанных отношениями [killlist_target](../../Creating_a_table/Local_tables/Plain_and_real-time_table_settings.md#killlist_target), ротация начнется с таблиц, которые не являются целями, и завершится на тех, что находятся в конце цепочки целей. Пример использования:

  ```shell
  sudo -u manticore indexer --rotate --all
  ```
* `--quiet` указывает `indexer` не выводить ничего, кроме ошибок. Это в основном используется для cron-задач или других скриптовых заданий, где вывод неважен или не нужен, кроме случая ошибки. Пример использования:

  ```shell
  sudo -u manticore indexer --rotate --all --quiet
  ```
* `--noprogress` не показывает сведения о ходе выполнения по мере их появления. Вместо этого итоговые данные о состоянии (такие как число проиндексированных документов, скорость индексирования и так далее) выводятся только по завершении индексирования. Если скрипт не запущен в консоли (или 'tty'), этот режим включен по умолчанию. Пример использования:

  ```shell
  sudo -u manticore indexer --rotate --all --noprogress
  ```
* `--remove_dups` логически удаляет повторяющиеся числовые ID документов при построении обычной таблицы. Первая проиндексированная строка для каждого ID остается видимой; более поздние строки с тем же ID помечаются как удаленные. Без этого параметра `indexer` сохраняет дублирующиеся ID. Пример использования:

  ```shell
  sudo -u manticore indexer --config /home/myuser/manticore.conf --remove_dups mytable
  ```
* `--buildstops <outputfile.text> <N>` просматривает источник таблицы, как если бы выполнял индексирование данных, и формирует список индексируемых терминов. Иными словами, он формирует список всех поисковых терминов, которые становятся частью таблицы. Обратите внимание, что он не обновляет саму таблицу, а просто обрабатывает данные так, как если бы индексировал их, включая выполнение запросов, заданных через [sql_query_pre](../../Data_creation_and_modification/Adding_data_from_external_storages/Fetching_from_databases/Execution_of_fetch_queries.md#sql_query_pre) или [sql_query_post](../../Data_creation_and_modification/Adding_data_from_external_storages/Fetching_from_databases/Execution_of_fetch_queries.md#sql_query_post). `outputfile.txt` будет содержать список слов, по одному на строку, отсортированный по частоте, где самые частые идут первыми, а `N` задает максимальное число слов, которое будет перечислено. Если его достаточно, чтобы охватить все слова в таблице, будет возвращено только это количество слов. Такой словарь можно использовать для функций клиентского приложения вроде "Вы имели в виду…", обычно вместе с `--buildfreqs`, описанным ниже. Пример:

  ```shell
  sudo -u manticore indexer mytable --buildstops word_freq.txt 1000
  ```

  Это создаст в текущем каталоге файл `word_freq.txt` с 1 000 наиболее частых слов в `mytable`, отсортированных по убыванию частоты. Обратите внимание, что файл будет относиться к последней таблице, индексированной при указании нескольких таблиц или `--all` (то есть к последней, перечисленной в конфигурационном файле).

* `--buildfreqs` работает вместе с `--buildstops` (и игнорируется, если `--buildstops` не указан). Поскольку `--buildstops` предоставляет список слов, используемых в таблице, `--buildfreqs` добавляет количество их вхождений в таблице, что полезно при определении того, следует ли считать некоторые слова стоп-словами, если они слишком часто встречаются. Это также помогает при разработке функций "Вы имели в виду…", где нужно знать, насколько чаще одно слово встречается по сравнению с другим, похожим. Например:

  ```shell
  sudo -u manticore indexer mytable --buildstops word_freq.txt 1000 --buildfreqs
  ```

  Это создаст `word_freq.txt`, как и выше, однако после каждого слова будет указано число раз, которое оно встретилось в данной таблице.

* `--merge <dst-table> <src-table>` используется для физического объединения таблиц, например если у вас есть [схема main+delta](../../Creating_a_table/Local_tables/Plain_table.md#Main+delta-scenario), где основная таблица меняется редко, а delta-таблица перестраивается часто, и `--merge` используется, чтобы объединить их. Операция идет справа налево: содержимое `src-table` анализируется и физически объединяется с содержимым `dst-table`, а результат остается в `dst-table`. В псевдокоде это можно выразить так: `dst-table += src-table` Пример:

  ```shell
  sudo -u manticore indexer --merge main delta --rotate
  ```

  В приведенном выше примере, где main — это основная, редко изменяемая таблица, а delta — более часто изменяемая, можно использовать описанное выше, чтобы вызвать `indexer` для объединения содержимого delta с основной таблицей и выполнить ротацию таблиц.

* `--merge-dst-range <attr> <min> <max>` запускает заданный фильтр диапазона при объединении. Точнее, поскольку слияние применяется к целевой таблице (как часть `--merge`, и игнорируется, если `--merge` не указан), `indexer` также отфильтрует документы, попадающие в целевую таблицу, и в итоговую таблицу попадут только документы, прошедшие заданный фильтр. Это можно использовать, например, в таблице, где есть атрибут `deleted`, и значение 0 означает `not deleted`. Такая таблица может быть объединена так:

  ```shell
  sudo -u manticore indexer --merge main delta --merge-dst-range deleted 0 0
  ```

  Любые документы, помеченные как удаленные (значение 1), будут удалены из новой объединенной целевой таблицы. Этот параметр можно указывать несколько раз в командной строке, чтобы добавить последовательные фильтры к слиянию; все они должны выполняться, чтобы документ вошел в итоговую таблицу.

* --`merge-killlists` (и более короткий псевдоним `--merge-klists`) меняет способ обработки kill list при слиянии таблиц. По умолчанию после слияния обе kill list отбрасываются. Это подходит для наиболее типичного сценария слияния main+delta. Однако при включении этого параметра kill list из обеих таблиц объединяются и сохраняются в целевой таблице. Обратите внимание, что kill list исходной (delta) таблицы всегда будет использоваться для подавления строк из целевой (main) таблицы.
* `--keep-attrs` позволяет повторно использовать существующие атрибуты при повторном индексировании. Каждый раз при перестроении таблицы для каждого нового ID документа проверяется наличие в "старой" таблице, и если он уже существует, его атрибуты переносятся в "новую" таблицу; если не найден, используются атрибуты из новой таблицы. Если пользователь обновлял атрибуты в таблице, но не в реальном источнике, который используется для таблицы, все обновления будут потеряны при повторном индексировании; использование `--keep-attrs` позволяет сохранить обновленные значения атрибутов из предыдущей таблицы. Можно указать путь для файлов таблицы, который будет использоваться вместо эталонного пути из конфигурации:

  ```shell
  sudo -u manticore indexer mytable --keep-attrs=/path/to/index/files
  ```

* `--keep-attrs-names=<attributes list>` позволяет указать, какие атрибуты нужно повторно использовать из существующей таблицы при повторном индексировании. По умолчанию в новую таблицу повторно используются все атрибуты из существующей таблицы:

  ```shell
  sudo -u manticore indexer mytable --keep-attrs=/path/to/table/files --keep-attrs-names=update,state
  ```

* `--dump-rows <FILE>` выгружает строки, полученные из SQL-источника(ов), в указанный файл в синтаксисе, совместимом с MySQL. Полученные дампы точно отражают данные в том виде, в каком их получает `indexer`, и помогают воспроизводить проблемы, возникающие во время индексирования. Команда выполняет получение данных из источника и создает как файлы таблицы, так и файл дампа.
* `--print-rt <rt_index> <table>` выводит полученные из источника данные как `INSERT` для таблицы real-time. Первые строки дампа будут содержать поля и атрибуты real-time (как отражение полей и атрибутов обычной таблицы). Команда выполняет получение данных из источника и создает как файлы таблицы, так и дамп-вывод. Команду можно использовать так: `sudo -u manticore indexer -c manticore.conf --print-rt indexrt indexplain > dump.sql`. Поддерживаются только SQL-источники. MVA не поддерживаются.
* `--sighup-each` полезен, когда вы перестраиваете много больших таблиц и хотите, чтобы каждая из них как можно скорее была ротирована в `searchd`. С `--sighup-each` `indexer` будет отправлять сигнал SIGHUP в `searchd` после успешного завершения работы над каждой таблицей. (Поведение по умолчанию заключается в отправке одного SIGHUP после построения всех таблиц).
* `--nohup` полезен, когда вы хотите проверить таблицу с помощью `indextool` перед фактической ротацией. `indexer` не будет отправлять SIGHUP, если этот параметр включен. Файлы таблицы переименовываются в `.tmp`. Используйте `indextool`, чтобы переименовать файлы таблицы в `.new` и выполнить ротацию. Пример использования:

  ```shell
  sudo -u manticore indexer --rotate --nohup mytable
  sudo -u manticore indextool --rotate --check mytable
  ```

* `--print-queries` выводит SQL-запросы, которые `indexer` отправляет в базу данных, а также события подключения и отключения SQL. Это полезно для диагностики и устранения проблем с SQL-источниками.
* `--help` (`-h` кратко) перечисляет все параметры, которые можно использовать в `indexer`.
* `-v` показывает версию `indexer`.

### Настройки конфигурации Indexer
Поведение `indexer` можно также настраивать в конфигурационном файле Manticore в секции `indexer`:

```ini
indexer {
...
}
```

#### lemmatizer_cache

```ini
lemmatizer_cache = 256M
```
Размер кэша лемматизатора. Необязательный параметр, значение по умолчанию — 256K.

Наша реализация [лемматизатора](../../Server_settings/Common.md#lemmatizer_base) использует сжатый формат словаря, который позволяет выбирать баланс между объемом памяти и скоростью. Она может выполнять лемматизацию непосредственно по сжатым данным, расходуя больше CPU, но меньше RAM, либо распаковывать и предварительно кэшировать словарь частично или полностью, расходуя меньше CPU, но больше RAM. Директива `lemmatizer_cache` позволяет точно задать, сколько RAM можно выделить под этот несжатый кэш словаря.

Сейчас доступны только словари [ru.pak, en.pak и de.pak](https://manticoresearch.com/install/). Это русские, английские и немецкие словари. Сжатый словарь имеет размер примерно от 2 до 10 МБ. Обратите внимание, что словарь все время находится и в памяти. Размер кэша по умолчанию — 256 КБ. Допустимый диапазон размера кэша — от 0 до 2047 МБ. Безопасно задавать слишком большой размер кэша: лемматизатор будет использовать только нужный объем памяти. Например, весь русский словарь после распаковки занимает примерно 110 МБ; поэтому установка `lemmatizer_cache` выше этого значения не повлияет на использование памяти. Даже если для кэша разрешено 1024 МБ, при необходимости всего 110 МБ будут использованы только эти 110 МБ.

#### max_file_field_buffer

```ini
max_file_field_buffer = 128M
```

Максимальный размер адаптивного буфера для файлового поля в байтах. Необязательный параметр, значение по умолчанию — 8 МБ, минимум — 1 МБ.

Буфер файлового поля используется для загрузки файлов, на которые ссылаются столбцы [sql_file_field](../../Data_creation_and_modification/Adding_data_from_external_storages/Fetching_from_databases/Processing_fetched_data.md#sql_file_field). Этот буфер адаптивный: он начинается с 1 МБ при первом выделении и растет в 2 раза, пока либо не загрузится содержимое файла, либо не будет достигнут максимальный размер буфера, заданный директивой `max_file_field_buffer`.

Таким образом, если файловые поля не указаны, буфер вообще не выделяется. Если все файлы, загружаемые во время индексирования, имеют размер, например, меньше 2 МБ, а значение `max_file_field_buffer` равно 128 МБ, пиковое использование буфера все равно составит только 2 МБ. Однако файлы больше 128 МБ будут полностью пропущены.

#### max_iops

```ini
max_iops = 40
```

Максимальное число операций ввода-вывода в секунду для ограничения I/O. Необязательный параметр, значение по умолчанию — 0 (без ограничения).

Параметр, связанный с ограничением I/O. Он ограничивает максимальное число операций ввода-вывода (чтения или записи) за любую одну секунду. Значение 0 означает, что ограничение не применяется.

`indexer` может создавать всплески интенсивного дискового I/O при построении таблицы, и может быть полезно ограничить его дисковую активность (оставив что-то и для других программ, работающих на той же машине, например `searchd`). Ограничение I/O помогает в этом. Оно работает за счет минимальной гарантированной задержки между последовательными дисковыми операциями I/O, выполняемыми `indexer`. Ограничение I/O может помочь уменьшить падение производительности поиска, вызванное построением. Эта настройка не действует на другие виды загрузки данных, например на вставку данных в таблицу real-time.

#### max_iosize

```ini
max_iosize = 1048576
```

Максимально допустимый размер операции I/O в байтах для ограничения I/O. Необязательный параметр, значение по умолчанию — 0 (без ограничения).

Параметр, связанный с ограничением I/O. Он ограничивает максимальный размер операции файлового ввода-вывода (чтения или записи) для всех операций, выполняемых `indexer`. Значение 0 означает, что ограничение не применяется. Чтения или записи, размер которых больше лимита, будут разбиты на несколько более мелких операций и будут учитываться как несколько операций настройкой [max_iops](../../Data_creation_and_modification/Adding_data_from_external_storages/Plain_tables_creation.md#max_iops). На момент написания все вызовы I/O и так должны быть меньше 256 КБ (размер внутреннего буфера по умолчанию), поэтому значения `max_iosize` выше 256 КБ не должны иметь эффекта.

#### max_xmlpipe2_field

```ini
max_xmlpipe2_field = 8M
```

Максимально допустимый размер поля для источника типа XMLpipe2 в байтах. Необязательный параметр, значение по умолчанию — 2 МБ.

#### mem_limit

```ini
mem_limit = 256M
# mem_limit = 262144K # same, but in KB
# mem_limit = 268435456 # same, but in bytes
```

Лимит использования RAM при построении обычной таблицы. Необязательный параметр, значение по умолчанию — 128 МБ. Принудительный лимит потребления памяти, который `indexer` не может превышать. Можно указывать в байтах, килобайтах (с постфиксом K) или мегабайтах (с постфиксом M); см. пример. Этот лимит будет автоматически увеличен, если его задать слишком низким и из-за этого I/O-буферы станут меньше 8 КБ; точная нижняя граница зависит от размера строящихся данных. Если буферы меньше 256 КБ, будет выдано предупреждение.

Максимально возможный лимит — 2047M. Слишком низкие значения могут ухудшить скорость построения обычной таблицы, но 256M–1024M должно хватить для большинства, если не всех наборов данных. Слишком высокое значение может привести к тайм-аутам SQL-сервера. На этапе сбора документов будут периоды, когда буфер памяти частично отсортирован и связь с базой данных не выполняется; из-за этого сервер базы данных может превысить тайм-аут. Это можно решить либо увеличением тайм-аутов на стороне SQL-сервера, либо уменьшением `mem_limit`.

#### on_file_field_error

```ini
on_file_field_error = skip_document
```

Как обрабатывать ошибки IO в файловых полях. Необязательный параметр, значение по умолчанию — `ignore_field`.
Когда возникает проблема при индексировании файла, на который ссылается файловое поле ([sql_file_field](../../Data_creation_and_modification/Adding_data_from_external_storages/Fetching_from_databases/Processing_fetched_data.md#sql_file_field)), `indexer` может либо обработать документ, считая это поле пустым, либо пропустить документ, либо полностью завершить индексирование с ошибкой. Директива `on_file_field_error` управляет этим поведением. Допустимые значения:
* `ignore_field`, обработать текущий документ без поля;
* `skip_document`, пропустить текущий документ, но продолжить индексирование;
* `fail_index`, завершить индексирование с сообщением об ошибке.

Проблемы, которые могут возникнуть: ошибка открытия, ошибка размера (файл слишком большой) и ошибка чтения данных. Предупреждения по любой проблеме будут выводиться всегда, независимо от фазы и настройки `on_file_field_error`.

Обратите внимание: при `on_file_field_error = skip_document` документы будут игнорироваться только если проблемы обнаружены на ранней фазе проверки, и **не** во время фактического разбора файла. `indexer` откроет каждый упомянутый файл и проверит его размер перед выполнением любой работы, а затем откроет его снова во время фактического разбора. Поэтому, если файл исчезнет между этими двумя попытками открытия, документ все равно будет проиндексирован.

#### write_buffer

```ini
write_buffer = 4M
```

Размер буфера записи в байтах. Необязательный параметр, значение по умолчанию — 1 МБ. Буферы записи используются для записи как временных, так и итоговых файлов таблиц при индексировании. Большие буферы уменьшают число требуемых записей на диск. Память под буферы выделяется дополнительно к [mem_limit](../../Data_creation_and_modification/Adding_data_from_external_storages/Plain_tables_creation.md#mem_limit). Обратите внимание, что будет выделено несколько (на текущий момент до 4) буферов для разных файлов, что пропорционально увеличивает использование RAM.

#### ignore_non_plain

```ini
ignore_non_plain = 1
```

`ignore_non_plain` позволяет полностью игнорировать предупреждения о пропуске таблиц, не являющихся обычными. Значение по умолчанию — 0 (не игнорировать).

### Планирование indexer через systemd

Есть два подхода к планированию запусков `indexer`. Первый — классический способ с использованием `crontab`. Второй — использование таймера `systemd` с пользовательским расписанием. Чтобы создать unit-файлы таймера, их нужно поместить в соответствующий каталог, где `systemd` ищет такие unit-файлы. В большинстве дистрибутивов Linux это обычно `/etc/systemd/system`. Вот как это сделать:

1. Создайте файл unit таймера для своего пользовательского расписания:
   ```shell
   cat << EOF > /etc/systemd/system/manticore-indexer@.timer
   [Unit]
   Description=Run Manticore Search's indexer on schedule
   [Timer]
   OnCalendar=minutely
   RandomizedDelaySec=5m
   Unit=manticore-indexer@%i.service
   [Install]
   WantedBy=timers.target
   EOF
   ```
   Подробнее о синтаксисе `OnCalendar` и примерах можно прочитать [здесь](https://www.freedesktop.org/software/systemd/man/latest/systemd.time.html#Calendar%20Events).

2. Отредактируйте unit таймера под свои нужды.
3. Включите таймер:
   ```shell
   systemctl enable manticore-indexer@idx1.timer
   ```
4. Запустите таймер:
   ```shell
   systemctl start manticore-indexer@idx1.timer
   ```
5. Повторите шаги 2-4 для всех дополнительных таймеров.
