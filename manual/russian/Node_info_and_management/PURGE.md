# PURGE

`PURGE` удаляет выбранные данные, связанные с таблицей. Цель очистки указывает, что именно будет удалено.

```sql
PURGE <target> FROM TABLE <table_name>;
```

Сейчас поддерживается только цель `BULK_IMPORT`.

## PURGE BULK_IMPORT

```sql
PURGE BULK_IMPORT FROM TABLE products [OPTION clear_sessions=0|1];
```

`PURGE BULK_IMPORT` удаляет весь промежуточный корневой каталог, используемый [массовым импортом](../Data_creation_and_modification/Adding_documents_to_a_table/Adding_documents_to_a_real-time_table.md#Bulk-import), включая каталоги и файлы, оставшиеся после прерванной загрузки. Выполняйте эту команду только после того, как убедитесь, что для таблицы не выполняется загрузка напрямую на диск.

Если у таблицы есть открытый или завершившийся ошибкой пул [общего массового импорта по HTTP](../Data_creation_and_modification/Adding_documents_to_a_table/Adding_documents_to_a_real-time_table.md#Shared-HTTP-bulk-import), оператор будет отклонен. С `OPTION clear_sessions=1` он сначала отменяет этот пул: неопубликованные данные отбрасываются, запросы, которые все еще пишут в пул, получают ошибку, его индексаторы останавливаются, таблица освобождается для обычных записей, а затем удаляется корень промежуточного хранилища. Фрагменты, опубликованные ранее, остаются в таблице. Пока пул присоединяет свои фрагменты после коммита, оператор отклоняется; повторите его после завершения коммита. В Windows, пока запрос все еще пишет в пул, оператор может не удалить корень промежуточного хранилища сразу после отмены пула, потому что остановленные индексаторы еще некоторое время держат файлы открытыми; повторите его.

Открытый пул держит таблицу зарезервированной, поэтому обычные записи в нее и другие массовые импорты в нее завершаются ошибкой, даже если все его клиенты уже отключились; [`SHOW LOCKS`](../Securing_and_compacting_a_table/Freezing_and_locking_a_table.md#SHOW-LOCKS) показывает такую таблицу с типом блокировки `write_allow_readers`. Если клиенты остановились или аварийно завершились до коммита, это освобождает таблицу и отбрасывает подготовленные ими данные:

```sql
PURGE BULK_IMPORT FROM TABLE products OPTION clear_sessions=1;
```

Чтобы вместо этого опубликовать подготовленные документы, выполните коммит пула запросом без документов, как описано в разделе [общий массовый импорт по HTTP](../Data_creation_and_modification/Adding_documents_to_a_table/Adding_documents_to_a_real-time_table.md#Shared-HTTP-bulk-import).

`OPTION clear_sessions=1` не отменяет приватные сеансы массового импорта: приватный сеанс освобождает таблицу с помощью `SET bulk_import=0` или при закрытии соединения.

Оператор требует существующую локальную таблицу реального времени либо секционированную или распределённую таблицу. Он удаляет только состояние подготовки данных непосредственно на диске и не изменяет схему таблицы или индексированные документы. Если корень подготовки отсутствует, оператор завершается успешно без изменений, поэтому его безопасно выполнять повторно. В режиме без конфигурации `DROP TABLE` также удаляет корень подготовки данных этой таблицы непосредственно на диске и отменяет её Shared-пул.

### Таблицы в кластере репликации

Для таблицы в кластере репликации оператор очищает только узел, на котором выполняется. Пока на этом узле хранится [фрагмент массового импорта таблицы](../Data_creation_and_modification/Adding_documents_to_a_table/Adding_documents_to_a_real-time_table.md#Bulk-import-into-a-replicated-table) для последующей команды подключения, оператор отклоняется с сообщением `a bulk_import chunk of table '<table>' is being replicated`:

* Если на любом узле кластера выполняется фиксация массового импорта в таблицу, повторите оператор после завершения фиксации. Не используйте в этот момент `OPTION clear_sessions=1`: он удалит копию фрагмента на этом узле, узел не сможет подключить фрагмент при поступлении команды и выйдет из кластера.
* Если массовый импорт в таблицу не выполняется, фрагмент остался, например потому, что узел, выполнявший загрузку, остановился до команды или этот узел в тот момент находился вне кластера. Удалите его с помощью `OPTION clear_sessions=1` либо перезапустите демон и повторите оператор.

### Секционированные и распределённые таблицы

Для секционированной или распределённой таблицы оператор очищает:

1. [Общий массовый импорт в секционированную таблицу](../Data_creation_and_modification/Adding_documents_to_a_table/Adding_documents_to_a_real-time_table.md#Shared-bulk-import-into-a-sharded-table), который координирует этот узел. Без параметра открытая или завершившаяся с ошибкой загрузка приводит к отклонению оператора, и ничего не очищается. Загрузка, публикация которой выполняется, приводит к тому же результату; повторите оператор после завершения фиксации.
2. Каждую локальную таблицу реального времени секционированной или распределённой таблицы; остальные локальные таблицы пропускаются.
3. Каждую таблицу каждого агента на каждом зеркале с помощью того же оператора.

С `OPTION clear_sessions=1` оператор отменяет каждый открытый Shared-пул этих таблиц, а не только пулы одной загрузки. Если узел, координировавший загрузку, остановился или аварийно завершил работу, выполните оператор с этим параметром на любом узле, содержащем секционированную таблицу. Убедитесь, что ни в одной из этих таблиц не выполняется частный массовый импорт.

Если некоторые таблицы не удаётся очистить, остальные всё равно очищаются. В сообщении об ошибке перечисляются все таблицы, для которых операция завершилась ошибкой, или недоступные агенты с указанием причины:

* `table '<shard>' is a target of an open shared bulk_import into a shard table`: в секции всё ещё хранится пул загрузки. Зафиксируйте загрузку на узле, который её координирует, или отмените её с помощью `OPTION clear_sessions=1`.
* Недоступный агент: повторите оператор после восстановления его узла.
* Любая другая ошибка: обработайте её так же, как для отдельной таблицы; см. выше.
